# 기록지 자동화(OMR) 검토 기록

> **상태: 검토 완료, 제작 대기.** 아직 아무것도 만들지 않았다.
> 2026-08-18 검토. 팀원 논의 후 제작 요청이 오면 이 문서에서 이어서 시작한다.

수기 기록지를 마킹(OMR) 방식으로 바꾸고, 사진을 올리면 엑셀이 나오게 하려는 계획.
지금은 경기 후 사람이 종이를 보고 엑셀에 손으로 옮겨 적고 있다.

이 문서는 **결정된 것 / 실제로 재본 숫자 / 아직 안 정한 것**을 나눠서 적는다.
숫자는 전부 팀 기록 엑셀(66시트)과 실제 측정에서 나온 것이고, 추측은 추측이라고 적었다.

## 1. 결론부터

| 항목 | 결론 |
|---|---|
| 홈페이지 한 페이지로 가능한가 | **가능** |
| 서버(서버리스 함수) 필요한가 | **불필요.** 전부 브라우저에서 처리 |

| OpenCV 필요한가 | **불필요.** 기준 마크 4개 → 기울기 보정 → 정해진 좌표 샘플링이면 끝 |

부수 효과로 사진이 인터넷에 안 올라가고, 인터넷이 끊겨도 동작한다(이미 PWA).

## 2. 기존 엑셀 파일 구조

`TalkFile_혼스탯.xlsx` 기준. **66시트 / 2024-04 ~ 2026-06 / 669KB.**

하루가 시트 한 장이고, 그 안에 **경기 블록이 1~6개** 들어간다.
3파전이면 6블록 = 혼A·혼B·혼C가 각 2경기 (실제 3경기를 양쪽 시점에서 기록).

블록 하나는 **17줄 간격**으로 반복된다:

```
혼 A                                   ← B1: 팀
1경기                                   ← B2
Team   1Q   2Q   3Q   4Q  Total        ← 헤더
혼A    12    9   10   10  =SUM(B4:K4)  ← 쿼터별 "증가분" (누적 아님!)
혼B     7   10    8   10  =SUM(B5:K5)
Play   14,10,24,35,12 | ...            ← 쿼터별 코트 위 5명 등번호
(빈 줄)
No Player MIN 2PM 2PA 2P% ... 비고     ← B~X열
14 홍재현  32   2   4  =IFERROR(E9/F9,0) ...
...
TEAM   =SUM(...)
```

- 컬럼: `B=No, C=Player, D=MIN, E~W=스탯, X=비고`
- `MIN = 출전 쿼터 수 × 8분` (8/16/24/32에 몰려 있음, 1,463건 중 1,330건)
- `Play` 줄은 쿼터마다 코트 위 5명의 등번호. **`①②③④` 동그라미에서만 나온다.**
- 시트명 규칙: `YYMMDD_경기유형` (예: `260628_자체3파전`)

### ⚠️ 서식이 5종류로 섞여 있다

| 형태 | 시트 수 |
|---|---|
| 현행 (`B=No, C=Player`, 2PM/2PA 분리) | **43** |
| 구형 (`B=Player`, No 컬럼 없음) | 23 |

→ **새로 만드는 시트만 현행 형식으로 쓰면 되고, 옛 시트는 건드릴 일이 없다.**

## 3. 엑셀 이어붙이기 — 안전 확인됨

"기존 누적 파일에 새 시트를 추가해서 돌려준다"가 서식을 깨뜨릴까 봐 걱정했는데,
**실제 파일로 읽고 다시 저장해서 대조해 봤다.**

| 검사 | 결과 |
|---|---|
| 셀 111,925개 값 비교 | 차이 **9개** (전부 `빈 문자열 → 빈 칸`, 의미 없음) |
| 서식 (채움·테두리·굵기·표시형식·정렬) | 차이 **0개** |
| 병합셀 4,937개 | 전부 유지 |
| 열 너비 · 수식 · 시트 66개 | 전부 유지 |

안전한 이유: 이 파일에 **차트·이미지·조건부서식·데이터유효성·매크로가 하나도 없다.**
순수한 표 + 수식 + 테두리라 왕복이 무사하다.

> ⚠️ 단, 이건 파이썬 라이브러리(openpyxl)로 시험한 결과다.
> **브라우저용 라이브러리로 한 번 더 확인해야 한다** — 제작 착수 시 첫 번째 할 일.

### 기존 파일에서 발견한 사소한 흠 (새로 만들 때 안 물려받으면 된다)

- `K17='=SUM(K7:K16)'` — 데이터는 9~16행인데 7행부터 더한다. 빈 칸이라 결과는 맞지만 범위가 어긋나 있다.
- `L4='=SUM(B4:K4)'` — 팀 이름 칸(B4)까지 포함. 텍스트는 무시되니 결과는 맞다.

## 4. 현행 수기 기록지 분석

**이미 절반은 OMR이다.** 2점/3점/자유투 칸에 `2 2 2 2 2…`가 미리 인쇄돼 있고,
시도 순서대로 표시하는 방식이다.

| 지금 방식 | OMR 적합성 |
|---|---|
| 슛: 한 시도에 칸 하나, **성공 ○ / 실패 ✗** | ❌ ○와 ✗는 칠해진 양이 비슷해 명암으로 구분 불가 |
| 카운트 스탯: `一 → T → F → 正` 획으로 세기 | ❌ 획 모양을 읽어야 해서 불가 |
| 출전 쿼터: `①②③④` 동그라미 | ✅ 그대로 OMR 가능 |
| 쿼터 점수: **누적**으로 기입 (14 → 20 → 23 → 39) | 엑셀은 **증가분**(14/6/3/17). 지금은 사람이 빼서 옮긴다 |

→ 슛의 ○/✗를 **성공 줄 / 실패 줄로 분리**하는 것이 새 양식의 핵심.
→ 쿼터 점수는 **종이는 누적 그대로 두고 프로그램이 빼면 된다** (현장에선 누적이 편하다).

> 실제로 6/16 1경기에서 종이 4쿼터 `39`, 엑셀 `40`으로 1점이 안 맞았다.
> 사진 판독 오류일 수도 있지만, 자동화하면 사라지는 종류의 오차다.

## 5. 새 양식(OMR 가안) 검토 결과

### 🔴 반드시 되살려야 할 것: 쿼터 칸 `①②③④`

가안에서 빠져 있는데, 이게 없으면 **MIN도 Play 줄도 만들 수 없다.**
선수당 버블 4개면 해결된다. (단, 8절의 4색 방식을 쓰면 색이 대신하므로 불필요해진다.)

### 🟡 버블 개수 재배치 — 실측 근거

66시트에서 **선수-경기 기록 1,681건**을 뽑아 실제 최댓값을 확인했다.

| 항목 | 실제 최대 | 99% | 95% | 평균 | 가안 | 권장 |
|---|---|---|---|---|---|---|
| 2점 시도 | 24 | 16 | 12 | 5.2 | 20 | **20** ✅ |
| 3점 시도 | 15 | 11 | 7 | 2.2 | 10 | **12** ⚠️ 부족 |
| 자유투 | 14 | 8 | 5 | 1.0 | 10 | **10** ✅ |
| 리바운드 | 20 | 14 | 10 | 4.1 | 15 | **15** ✅ |
| 어시스트 | 9 | 7 | 5 | 1.8 | 15 | **10** 🔻 과함 |
| 스틸 | 7 | 4 | 3 | 0.8 | 15 | **8** 🔻 과함 |
| 블락 | 9 | 3 | 1 | 0.2 | 15 | **8** 🔻 과함 |

재배치하면 선수당 **160개 → 145개** (쿼터 4개를 더하고도 줄어든다).
**남는 자리로 버블을 키울 것** — 가안은 지름 3mm 안팎으로 보이는데 경기 중에 칠하기엔 작다.

### 🟢 선수 줄 수 — 두 종류로 뽑는 게 낫다

경기당 인원: **6~8명이 84%**, 최대 11명(대회).
→ **자체전용 8줄(버블 크게) / 대회용 12줄** 두 가지.

### 🟢 손글씨 칸은 전부 없앨 수 있다

| 지금 손글씨 | 없애는 방법 |
|---|---|
| 선수 이름 · NO. | 팀 편성에서 **미리 인쇄** |
| 날짜 / GAME No. / 상대팀 | **미리 인쇄** |
| 쿼터 점수 | 십의자리·일의자리 **버블** (0~99) — 자리를 먹지만 사람 손이 완전히 빠짐 |
| 비고 | 유일하게 남김 → **검수 화면에서 타이핑** |

## 6. 손글씨는 읽을 수 없다 (그래서 없애는 것)

| | 브라우저만으로 |
|---|---|
| 마킹된 버블 | ✅ 거의 확실 |
| 색 구분 (검정/빨강) | ✅ 잘 됨 |
| 인쇄체 숫자 | 🔺 되긴 하나 오차 있음 |
| **손글씨 숫자** | ❌ 실용 수준 아님 |
| **손글씨 한글 이름** | ❌ 전혀 안 됨 |

브라우저에서 도는 무료 문자인식(tesseract.js)은 **인쇄 활자용**이라 손글씨는 거의 못 읽는다.
유료 AI API를 쓰면 읽히지만, 그건 애초에 피하려던 방향이다.

## 7. 색 인식 — 된다

사진은 색 정보를 그대로 담고 있으므로, 칸마다 "얼마나 진한가"에 더해 "무슨 색인가"를 재면 된다.

| 상태 | 밝기 | 색 선명도 |
|---|---|---|
| 빈 칸 | 밝음 | 없음 |
| 검정 | 어두움 | **없음** |
| 빨강 | 중간 | **강함** |

검정("색 없는 어두움")과 빨강("색이 뚜렷한 중간 밝기")은 멀리 떨어져 있어 헷갈리지 않는다.
○/✗ 구분보다 훨씬 쉽다.

### 필수 조건: 기록지에 색 견본을 인쇄할 것

체육관 조명 색온도에 따라 폰 카메라가 흰 종이를 누렇게/푸르스름하게 찍는다.
→ 귀퉁이에 **흰색·검정·빨강 견본 사각형**을 인쇄해두고, 사진마다 견본으로 먼저 맞춘 뒤 판독한다.
기준 마크(기울기 보정용)와 같은 자리에 넣으면 된다.

### 용도 ①: 취소 — 조건부

**칸 안에 덧칠하면 안 된다.** 검정 위에 빨강을 덧칠하면 검정이 이겨서 그냥 시커먼 칸이 된다.
→ **그 칸을 가로지르는 빨간 줄**로 표시. 판독은 "이 칸 주변에 빨간색이 있나?"만 보면 되므로 모양 인식이 아니다.

> 취소가 꼭 필요하진 않다. 검수 화면에서 고칠 수 있다.
> 다만 현장에서 "잘못 칠했다"를 남겨둘 수 있으면 나중에 기억을 더듬을 일이 없다.

### 용도 ②: 쿼터 구분 — 강력 추천

**4색 볼펜 하나로 1Q 검정 / 2Q 빨강 / 3Q 파랑 / 4Q 초록.**

얻는 것:
1. **`①②③④` 칸이 필요 없어진다** — 색만 봐도 출전 쿼터를 알 수 있다 → MIN·Play 자동
2. **쿼터별 개인 스탯**이 공짜로 생긴다 (지금 엑셀에 없는 정보)
3. **오류 검사가 쿼터 단위로 촘촘해진다** — "3쿼터가 4점 안 맞는다"까지 좁혀준다

주의:
- **파랑·초록은 빨강보다 어렵다.** 볼펜 잉크가 옅어 색이 덜 뚜렷하다. 견본 패치로 되지만 여유가 적다.
- 기록자가 색 바꾸는 걸 잊으면 그 쿼터 전체가 앞 쿼터로 붙는다 → 위 3번 검사로 잡힌다.

### 단계적 도입 (각 단계가 앞 단계를 안 깨뜨린다)

| 단계 | 색 | 얻는 것 | 위험 |
|---|---|---|---|
| 1 | 검정만 | 원래 하려던 것 전부 | 없음 |
| 2 | + 빨강 (취소) | 현장 수정 | 낮음 |
| 3 | 4색 (쿼터) | 쿼터별 스탯 + 쿼터 칸 제거 | 중간 |

**4색을 전제로 설계하되 1단계로 시작한다.** 종이는 그대로 두고 판독 규칙만 늘어난다.

## 8. 검수 화면은 필수

체육관 조명·그림자·구겨진 종이·폰 각도 때문에 OMR은 100%가 안 나온다.

→ 업로드 후 **인식 결과를 표로 전부 보여주고, 애매한 칸은 빨갛게 표시해 손으로 고친 뒤 다운로드.**
이게 있으면 최악의 경우도 "지금처럼 손으로 입력"하는 수준이지, 데이터가 조용히 틀어지지 않는다.

### 넣을 검사 목록 (과거 66시트로 미리 돌려본 결과)

| 검사 | 과거 데이터에서 |
|---|---|
| 1. 팀 쿼터 점수 합 = 개인 득점 합 | **205블록 중 18건(9%)이 불일치** (최대 43점 차) |
| 2. **교차 검증** — 3파전은 같은 경기가 두 시점으로 기록됨 | `260628` 3경기 전부 양쪽 점수 일치. 한쪽을 잘못 읽으면 바로 걸린다 |
| 3. 쿼터별 대조 (4색 도입 시) | 오류를 쿼터 단위로 좁혀줌 |
| 4. Play 줄이 쿼터마다 5명인가 | **36건이 5명 아님** (6~8명) |
| 5. 출전 쿼터 수 × 8분 = MIN | **1,463건 중 133건이 8의 배수 아님** (대회 때 쿼터 시간이 다른 듯 → 경고만) |
| 6. 성공 ≤ 시도, 같은 선수 두 팀 동시 등장 | — |

2번이 특히 강력하다. 이 팀의 기록 방식(3파전을 양쪽 시점에서 기록)에서만 가능한 검사다.

## 9. 전체 흐름

```
1. 팀 편성에서 팀을 짠다              ← 이미 있는 기능 (2팀/3팀, TEAM_LETTERS = A/B/C)
2. 이미지 내보내기로 팀 공유           ← 이미 있는 기능
3. 인쇄용 기록지 PDF 출력  ★신규       ← 이름·날짜·대진이 미리 채워진 6장
4. 현장에서 수기 작성
5. 사진 + (선택) 누적 엑셀 업로드  ★신규
6. 검수 → 업데이트된 엑셀 다운로드  ★신규
```

### 3번은 반드시 **PDF**로 (엑셀 ❌)

| | 엑셀 | 이미지(PNG) | **PDF** |
|---|---|---|---|
| 버블 위치 고정 | ❌ 프린터·설정 따라 변함 | 🔺 배율 의존 | ✅ mm 단위 고정 |
| 기준 마크·색 견본 배치 | ❌ | 🔺 | ✅ |

**OMR은 좌표가 생명이다.** 지금까지 엑셀로 뽑아 써도 문제없던 건 사람이 읽었기 때문이다.
인쇄 시 "실제 크기(100%)" 안내가 필요하지만, 기준 마크 4개가 있으면 배율이 틀려도 보정된다.

**다운로드(6번)는 엑셀이 맞다** — 받아서 직접 편집해야 하므로.

### 팀 편성과 이미 맞아떨어지는 것

### 엑셀은 "다시 쓰지" 않고 "덧댄다"

브라우저용 엑셀 라이브러리(SheetJS 등)는 파일을 읽어서 다시 쓴다. 그러면
셀 서식·열 너비·틀 고정이 통째로 날아간다 — 2024년부터 쌓아온 파일에는
쓸 수 없는 방식이다.

그래서 `js/xlsx-lite.js`를 직접 만들었다. xlsx는 결국 zip이므로,
**압축된 부품을 원본 바이트 그대로 옮기고 시트 XML 한 개만 고쳐 넣는다.**
`styles.xml`도 `sharedStrings.xml`도 손대지 않으니 서식이 그대로 남는다.
새로 붙는 줄의 셀에는 기존 마지막 줄의 서식(`s` 속성)을 물려줘서 표가 이어져 보인다.

확인한 것 (openpyxl로 왕복 검사):
- 인라인 문자열 파일 / 공유 문자열 파일 양쪽 다 읽고 붙인다
- 머리글 굵게·색·테두리, 열 너비, 틀 고정, 건드리지 않은 다른 시트 — 모두 보존
- `dimension` 범위도 같이 늘려 둔다
- 같은 원본에서 매번 새로 열어 붙이므로, 다운로드를 두 번 눌러도 두 번 붙지 않는다

필요 조건은 `DecompressionStream`/`CompressionStream("deflate-raw")`
(크롬 80+, 사파리 16.4+, 파이어폭스 113+). 안 되는 브라우저에서는 바로 알려준다.

### 파일 이름은 아스키만 쓴다

크로미움은 `a[download]` 이름에 한글이 섞이면 이름을 통째로 버리고 확장자 없는
`download`로 내려받는다 — 더블클릭해도 안 열리는 파일이 된다. 실제로 측정해서
확인했다. 그래서 `spirit-stats-260823_1.xlsx` 같은 아스키 이름을 쓰고, 사람이
올린 파일 이름은 아스키일 때만 살린다.

### 확률 열은 분수로 넣고 서식만 퍼센트로

`2점야투 / 3점야투 / 전체야투 / 자유투확률` 네 열은 **0.5455 같은 분수를 넣고**
엑셀 내장 서식 10번(`0.00%`)을 입혀 `54.55%` 로 보이게 한다. 값을 `54.55` 로
넣어버리면 나중에 평균을 낼 때 100배 틀린 숫자가 나온다.

소수 둘째 자리 퍼센트를 보이려면 분수는 넷째 자리까지 있어야 한다
(6/11 = 0.5454… → 0.5455 → 54.55%. 셋째 자리에서 자르면 54.50% 가 되어버린다).

새로 붙는 줄만 퍼센트로 보이면 한 열이 두 가지 모양으로 갈리므로, **원래 있던
줄에도 같은 서식을 입힌다.** 값은 건드리지 않고 보이는 모양만 바꾼다.
글꼴·테두리·배경은 그대로다 — 기존 서식(xf)을 복사해서 숫자 서식만 바꾼 판을
`cellXfs` 맨 뒤에 덧붙이므로 기존 서식 번호가 하나도 안 밀린다.

⚠️ 2026-08 이전에 쌓인 줄은 원래 소수 셋째 자리까지만 저장돼 있어서
`0.545 → 54.50%` 로 보인다. 없던 자릿수는 되살릴 수 없다.

### GameScore 와 MOM

John Hollinger 의 GameScore 를 `js/gamestats.js` 의 `gameScore()` 로 넣었다.
화면 표의 `GS` 열, 결과 이미지의 `GS` 열, 글 요약의 `MOM` 줄에 나온다.
결과 이미지에서는 MOM 줄에 옅은 배경을 깔고 아래 줄에 이름을 밝혀 둔다.

```
pts + 0.4·fgm − 0.7·fga − 0.4·(fta − ftm)
    + 0.7·oreb + 0.3·dreb
    + stl + 0.7·ast + 0.7·blk − 0.4·pf − to
```

**🔴 정확히 내려면 기록지에 공격/수비 리바운드 칸이 나뉘어야 한다.**
원식은 공격 리바운드에 0.7, 수비 리바운드에 0.3 을 준다. 우리 기록지는 리바운드를
하나로만 세므로 둘을 나눌 수가 없다. 그래서 지금은 섞은 가중치를 쓴다.

```
REB_WEIGHT = 0.7 × OREB_SHARE + 0.3 × (1 − OREB_SHARE) = 0.42   (OREB_SHARE = 0.3)
```

`OREB_SHARE = 0.3` 은 **우리 기록으로 검증한 값이 아니라 통념값**이다. 나머지 항목
(득점·야투·자유투·스틸·어시·블락·파울·턴오버)은 전부 정확하므로, 순위가 크게
뒤집히지는 않지만 리바운드가 많은 선수일수록 오차가 커진다.

해결책: 리바운드 24칸을 **공격 8 / 수비 16 으로 나누기.** 버블 개수는 그대로라
가로 폭이 늘지 않는다(칸 사이 여백만 조금). 다만 수비 리바 16 이 한 경기 최대치
(관측 18)보다 작아질 수 있어, 8/16 대신 8/18 로 갈지 판단이 필요하다.

**한 경기 = 두 팀.** 기록지는 팀마다 한 장씩 나오지만, 화면과 결과표는 두 장을 한
경기로 묶는다(`game.teams[0]`, `[1]`). 그래야 MOM 을 원래 규칙대로 **이긴 팀에서**
뽑을 수 있다. 비겼을 때만 두 팀을 통틀어 고른다.

진 팀에 GameScore 가 더 높은 선수가 있는 경우가 흔하다(예: 16.4 인데 MOM 은 11.5).
결과 이미지 아래에 "MOM 은 이긴 팀에서 뽑습니다 — 전체 최고는 …"이라고 밝혀 둔다.
안 그러면 그림이 틀린 것처럼 읽힌다.

**"데일리 MOM"은 아직 안 된다.** 이 화면은 경기 한 개만 들고 있다. 하루치 MOM 은
그날 여러 경기를 모아야 한다 (3파전이면 3경기).

### 결과 이미지에 비고를 넣지 않는다

비고는 "기록지 칸이 모자라 옆에 적었다" 같은, **옮겨 적는 사람이 자기한테 남기는
메모**다. 밴드에서 볼 사람에게는 뜻이 닿지 않고, 사진 판독이 붙어도 손글씨라 못 읽는다.
그래서 결과 이미지에서는 뺐다. 입력 화면과 누적 엑셀에는 그대로 남는다 — 검토 화면이
"비고가 적혀 있습니다"라고 한 번 짚어준다.

### 이미 넣은 경기를 나중에 고칠 때

숫자를 잘못 옮긴 걸 나중에 발견하면, 화면에서 고치고 **그 엑셀을 다시 올린다.**
같은 경기(`날짜` 열의 `260823_1` + `팀` 열)가 이미 있으면 붙이지 않고
**그 자리에서 값만 갈아끼운다.** 짝은 (팀, 이름)으로 맞춘다 — 사람이 고치는 건
보통 숫자이지 이름이 아니다.

- 이미 있는 줄 → 그 행을 고쳐 넣는다 (몇 행인지 화면에 보여준다)
- 새로 생긴 선수 → 맨 아래에 붙인다
- 이제 없는 선수인데 시트에는 남은 줄 → **몇 행인지 알려만 준다**

마지막 것을 우리가 지우지 않는 이유: 줄을 지우면 뒤 줄 번호가 전부 밀리고, 그 줄을
가리키던 수식이 어긋난다. 엑셀에서 사람이 지우면 엑셀이 수식을 알아서 따라 고쳐준다.

수식이 든 칸(`=H2/I2` 같은 것)은 덮어쓰지 않고 그대로 둔다. 덮으면 수식이 사라진다.

### 글로 남기는 요약

`summaryText()`가 최종 점수·쿼터별 누적·팀 기록·오늘의 기록에 더해
"짚어볼 점"(야투 호조/부진, 3점 폭발, 턴오버 과다, 리바운드 우세, 접전/대승,
특정 쿼터 격차)을 붙인다. 숫자를 다시 늘어놓지 않고 눈에 띄는 것만 짚는다.

## 11-1. 화면은 "사진 → 결과 두 개"가 전부다

한 번 잘못 만들었다가 되돌린 기록이다. 출력 쪽을 만들면서 입력 폼을 잔뜩 붙였더니
화면이 **손으로 넣는 곳**처럼 되어버렸다. 이 도구의 목적은 그게 아니다.

지금 `#/stats` 는 이 순서다.

1. **기록지 사진** — 여러 장 한 번에. 두 팀 것을 같이 올린다.
2. **오늘 경기 결과** — 밴드용 이미지 + 붙여넣을 글
3. **누적 기록** — 쓰던 엑셀에 이어 붙인 파일
4. *숫자 고치기* — 접혀 있다. 판독이 틀렸을 때만 펴는 곳

숫자를 손으로 넣는 표는 4번 안에만 있다. 밖으로 꺼내지 말 것.

### 화면이 흔들리던 이유

`.stats-table thead th` 에 `position: sticky; top: 0` 이 걸려 있었다. 표가 한 개일
때는 괜찮았는데 두 팀으로 늘어난 뒤부터 첫 표의 머리줄이 화면 위에 붙은 채 두 번째
표 위로 떠서 글자가 겹쳤다. 세로 고정을 떼고, 가로로 밀 때 따라오는 이름 칸
(`.stats-sticky`, `left: 0`)만 남겼다.

결과 이미지도 가로 스크롤 상자에 넣어 뒀는데, 한 화면에 옆으로 미는 상자가 여러 개
있으면 화면이 좌우로 흔들린다. 폭에 맞춰 줄이는 쪽으로 바꿨다.

### 승률왕 카드는 그냥 누르면 열린다

1초 길게 누르기로 만들었다가 뺐다. 올해는 그 자리 주인이 바뀌지 않아 위치가 고정이고,
길게 누르기는 아는 사람만 쓸 수 있어서 오히려 걸림돌이었다.

## 11-2. 판독기 — 붙었다

`js/sheetform.js` + `js/sheetread.js`.

### 종이와 판독기가 같은 좌표를 본다

가장 조심한 것: **인쇄한 종이와 판독기가 좌표를 따로 들고 있으면 안 된다.** 따로 두면
양식을 한 번 손볼 때마다 판독이 조용히 어긋난다.

그래서 `sheetform.js` 하나가 인쇄용 HTML 도 만들고, 그 결과를 그대로 재서
(`measureSheet`) 좌표도 낸다. 브라우저가 배치한 결과를 재는 것이라 두 숫자가
달라질 방법이 없다. 버블마다 `data-bub` 아이디가 붙어 있고, 그게 판독 결과를 어느
기록으로 옮길지 정하는 열쇠다.

```
q:<선수>:<쿼터>                        출전
s:<선수>:<p2|p3|ft>:<반기>:<번째>:<m|x>  슛
c:<선수>:<reb|ast|…>:<번째>             카운트
```

기록지 한 장에 버블 1,728개 — 출전 36 · 슛 1,080 · 카운트 612.

### 읽는 순서

1. **네 귀퉁이 표식 찾기** — 오츠 문턱값으로 어두운 덩어리를 모으고, 크기(종이 폭의 2%)·
   정사각형 비율·채움률로 거른 뒤 네 귀퉁이에 가장 가까운 것을 하나씩 고른다.
2. **호모그래피** — 그 네 점으로 종이 mm → 사진 px 변환을 푼다(8×8 선형계).
3. **버블 재기** — 안쪽 9점을 찍어 평균을 내고, 바로 바깥 종이 4점 중 **가장 밝은 값**과
   견준다. 그늘이 져도 그 자리 종이와 비교하니 문턱값이 따라간다.
   빨강 판정은 R − (G+B)/2 > 26.

### 못 찾으면 사람이 찍는다

종이가 잘려 찍히거나 그늘이 심하면 표식을 못 찾는다. 실제로 처음 올라온 사진 두 장이
모두 귀퉁이가 잘려 있었다. 그래서 실패하면 **사진 위에서 네 귀퉁이를 순서대로 눌러
주는 화면**으로 넘어간다 — 그 뒤 과정은 자동과 똑같다. 이게 있어야 실전에서 안 막힌다.

### 쿼터 점수는 손글씨에서 읽지 않는다

넣은 슛마다 어느 쿼터인지가 이미 색(검정=홀수, 빨강=짝수)과 줄(전반/후반)에 적혀 있다.
그래서 **쿼터별 팀 득점은 버블에서 그대로 계산된다.** 종이 위쪽 손글씨 표는 이 계산이
맞는지 대조하는 용도로만 쓴다 — 브라우저는 손글씨를 못 읽으니 그게 맞는 역할이다.

`sheet-readtest.html` — 정답을 칠한 기록지를 굽고, 기울이고 그늘을 씌운 뒤 다시 읽어
정답과 대조한다. 정면 / 살짝 기울임 / 많이 기울임 / 기울임+그늘 / 어두운 바닥
다섯 경우 모두 70칸을 어긋남 0으로 읽는다. 쿼터 점수도 손계산과 일치(5/14/20/23).

**아직 합성 시험이다.** 진짜 사진에는 흔들림·JPEG 뭉개짐·덜 칠한 자국이 섞인다.
실제 사진으로 맞춰보는 건 귀퉁이가 다 나온 사진을 받은 뒤에 한다.

### 남은 것: 줄이 누구인지

판독기는 "몇 번째 줄"까지만 안다. 이름은 인쇄된 글자라 못 읽는다. 지금은 표시가 있는
줄만 사람이 골라준다(5명이면 다섯 번). 사이트에서 기록지를 뽑을 때 명단을 같이
저장해 두면 이것도 없앨 수 있다 — 다음 작업.

## 11-3. 실제 사진으로 처음 돌려본 뒤 — 세 가지가 틀렸다

합성 시험은 다 통과했는데 진짜 사진에서는 엉망이었다(한 장은 334칸, 다른 장은 54칸).
원인 셋을 찾아 고쳤다.

### ① 기준값을 이웃 버블 위에서 재고 있었다 — 가장 큰 원인

빈 칸 기준을 "버블 바로 바깥 종이"에서 얻었는데, 표본 위치가 틀렸다.

```
버블 간격   가로 4.10mm · 세로 3.50mm
표본 위치   가로 3.36mm · 세로 3.12mm   ← 이웃 버블 중심의 82% / 89% 지점
```

즉 종이가 아니라 **이웃 버블 위**를 재고 있었다. 옆 칸이 칠해졌는지에 따라 기준값이
널뛰어서, 어두운 사진은 넘치게 밝은 사진은 모자라게 읽혔다.

지금은 **이웃 버블들의 중앙값**을 기준으로 쓴다. 한 장 1,728칸 중 칠하는 건 백 몇 개라
중앙값은 거의 항상 빈 칸이다. 조명이 한쪽만 어두워도 그 근처 중앙값이 같이 어두워지니
따라간다. 문턱값도 고정하지 않고 그 비율들에 오츠를 돌려 정한다.

### ② 접힌 자국 — 네 귀퉁이만으로는 못 편다

기록지를 반으로 접어 오면 접힌 선을 경계로 좌우가 서로 다른 면이 된다. 네 귀퉁이
하나로 편 좌표는 가운데에서 몇 mm씩 어긋나 옆 칸을 읽는다. 시험에서 70칸 중 39칸까지
떨어졌다.

**종이 위·아래 가운데에 표식(5mm)을 하나씩 더 넣었다.** 접힌 선이 곧 경계라,
왼쪽·오른쪽을 따로 펴면 딱 맞는다. 넣고 나니 70/70.

⚠️ 이 표식이 없는 예전 기록지는 여전히 접힌 만큼 어긋난다. 그런 종이는 펴서 찍거나
「귀퉁이 다시」에서 여섯 점을 직접 찍어야 한다.

### ③ 출전 열이 통째로 안 읽혔다

기준값을 구하는 격자 칸(22mm)에 버블이 24개는 있어야 중앙값을 쓰게 해뒀는데,
**출전 열은 한 칸에 다섯 개뿐**이라 기준을 못 구하고 전부 빈 칸으로 처리됐다.
표본이 모자라면 칸을 한 겹씩 넓혀 가며 모으도록 고쳤다.

### 지금 시험 결과

정면 / 많이 기울임 / 한쪽 그늘 45% / 가운데 반사 / 흐림+JPEG / 접힌 자국 /
그리고 이 전부를 겹친 "실전 비슷" — **일곱 경우 모두 70칸 어긋남 0.**

### 판독 확인 그림

안 맞을 때 눈으로 원인을 찾으라고 넣었다. 사진 위에 판독기가 잡은 종이 테두리(노랑)와
칸마다 본 자리를 겹쳐 보여준다. 초록 = 빈 칸, 파랑 = 검정 마킹, 빨강 = 빨강 마킹.
테두리가 실제 종이와 어긋나 있으면 귀퉁이를 잘못 잡은 것이다.

## 11-4. 선수 이름은 뽑을 때 적어 둔다

판독기는 "몇 번째 줄"까지만 안다 — 이름은 **인쇄된 글자**라 못 읽는다(손글씨가 아니라
인쇄 글자여도 브라우저에는 OCR 이 없다).

그래서 읽는 쪽이 아니라 **뽑는 쪽**에서 해결했다. 팀 편성에 「📄 기록지 출력」을 넣고,
뽑을 때 그 종이에 인쇄한 명단을 `260823_1|혼 A` 같은 열쇠로 저장해 둔다. 사진을 올려
팀만 고르면 줄 번호로 이름이 되돌아온다.

사이트 밖에서 뽑은 기록지는 예전처럼 줄마다 고르면 된다.

## 11-5. 못 믿을 판독은 못 믿겠다고 말한다

판독이 어긋나면 숫자가 **안 나오는 게 아니라 그럴듯한 헛것이 나온다.** 실제로 종이에
비어 있는 (예비) 줄에 67점이 찍혔다. 그걸 조용히 보여주면 사람이 믿고 엑셀에 넣는다.

그래서 `judgeReading()` 이 판독 결과를 훑고, 아래 중 하나라도 걸리면 **「판독 실패」**로
표시한다. 숫자는 접어 두고, 「읽은 기록 넣기」에서도 빼 버린다.

- 칠해진 칸이 20개 미만 / 420개 초과
- 한 줄에 40점 초과 (여러 줄이 한 줄로 쏠린 것)
- 슛 기록의 55% 넘게가 한 줄에 몰림 (세로가 어긋남)
- 기록은 있는데 출전 표시가 거의 없음 (왼쪽 끝이 어긋남)

기준은 실제 기록지에서 나온 값이다. **없는 기능을 있는 척하지 않는 것과 같은 이유로,
틀린 판독을 맞는 척 보여주지 않는다.**

### 아직 못 고친 것 — 실제 사진

합성 시험 일곱 경우는 다 통과하는데, 실제로 찍어 온 기록지(가운데 표식이 없고 접혀 있는
예전 양식)는 여전히 못 읽는다. 원인을 더 좁히려면 **판독 확인 그림**이 있어야 한다 —
종이를 어디로 잡았는지, 칸을 어디서 봤는지가 거기 다 보인다. 그림 없이 짐작으로 고치는
것은 이미 두 번 헛수고를 했다.

## 11-6. 인쇄가 통째로 망가졌던 세 가지

「기록지 출력」을 처음 실제로 인쇄해 보니 못 쓸 물건이 나왔다. 원인 셋 — 다 다시
밟기 쉬운 것들이라 적어 둔다.

### ① zoom 은 transform 이 아니다

미리보기에서 297mm 짜리를 `zoom: 0.34` 로 줄여 놓고, 인쇄 CSS 에서는 `transform: none`
만 되돌렸다. `zoom` 은 그대로 남아서 **종이가 34% 크기로 찍혔다.**

### ② `@page{size:A4 landscape}` 가 안 먹었다

나온 PDF 가 210×297 **세로**였다. 기록지는 297mm 폭이라 세로 종이에는 애초에 안 들어간다.
치수를 직접 적으니(`size: 297mm 210mm`) 먹었다. `preferCSSPageSize` 로 뽑아 재보면
297.0 × 209.9mm 가로가 나온다.

### ③ 🔴 배경 그래픽이 꺼져 있으면 표식이 안 찍힌다

가장 위험한 것. 네 귀퉁이 표식은 CSS `background` 인데, **크롬 인쇄창의 "배경 그래픽"은
기본이 꺼짐**이다. 그대로 두면 표식이 아예 안 찍히고, 그러면 사진 판독이 원천적으로
불가능한 종이가 나온다. 그런데 종이는 멀쩡해 보인다 — 표가 다 있으니까.

`print-color-adjust: exact` 를 기록지에 걸어 강제하고, 인쇄 안내에도 적어 뒀다.

### 확인 방법

브라우저 인쇄창을 눈으로 믿지 말고 `page.pdf({preferCSSPageSize:true, printBackground:true})`
로 실제 PDF 를 뽑아 MediaBox 치수를 재고, `emulateMedia({media:"print"})` 로 찍히는
모습을 그대로 캡처해 볼 것.

## 11-7. 왜 "하나도 안 맞았나" — 귀퉁이 네 개로는 부족했다

기록지를 인쇄해서 실제로 쓰고 찍어 올렸더니 **내용이 하나도 안 맞았다.** 판독은
"성공"했고 숫자도 그럴듯하게 나왔는데 종이와 전혀 달랐다. 짐작으로 두 번 고쳐 봤다가
두 번 다 모자랐으므로, 이번에는 **재고** 고쳤다.

### 잰 것

실제 사진을 판독기에 통과시킨 뒤, 버블마다 "예상한 자리"와 "인쇄된 동그라미가 실제로
있는 자리"의 차이를 전부 재서 위치별로 모았다.

| 종이 위 자리 | 가로 어긋남 | 세로 어긋남 |
|---|---|---|
| 왼쪽 위 | -1px | -2px |
| 가운데 | +2px | 0px |
| 오른쪽 아래 | **+12px** | **-13 ~ +12px** |

버블 세로 반지름이 **9.4px**(1.27mm)이다. 즉 종이 안쪽에서는 **한 칸을 통째로 넘어가
옆 줄을 읽고 있었다.** 문턱값이나 색 판정을 아무리 손봐도 고쳐질 수 없는 종류의 문제다.

원인은 하나가 아니다 — 종이가 완전히 평평하지 않고, 휴대폰 렌즈가 가장자리를 휘고,
인쇄 배율도 딱 맞지 않는다. 공통점은 **전부 종이 안쪽에서 생긴다**는 것이다. 귀퉁이
네 점으로 푼 호모그래피는 그 네 점에는 정확히 맞춰지지만 **그 사이는 아무것도 잡아주지
않는다.** 표식이 네 개뿐이니 당연한 일이었다.

### 고친 것 — 네 변에 눈금 표식을 깔았다

종이 네 변을 따라 3.4mm 검은 사각형을 줄지어 인쇄한다(좌우 10개씩, 상하 9개씩, 모두 38개).
판독기는 이걸 찾아 "예상 자리 → 실제 자리" 차이를 변마다 재고, 그 차이를 안쪽으로
부드럽게 이어 붙여(쿤스 패치) 종이 전체의 밀림 지도를 만든다.

그다음 **인쇄된 동그라미 자체**로 마지막 미세 조정을 한다. 제대로 맞은 자리에서는
테두리가 가장 어둡다는 성질을 쓰는데, 찾는 범위를 버블 반지름의 0.35배로 **좁게** 묶는 게
핵심이다. 넓게 잡았다가 옆 줄에 들러붙어 오히려 20 → 34로 망가뜨려 본 적이 있다.
안쪽 밝기까지 같이 보는 방식도 시도했다가 **칠해진 칸**(안쪽도 까맣다) 때문에 틀어졌다.
테두리만 보면 칠한 칸은 어느 쪽으로 밀어도 비슷하게 어두워서 최저점을 옮기지 않는다.

### 얼마나 나아졌나

실제 사진에서 잰 밀림을 그대로 흉내 낸 합성 기록지(1,728칸)로 채점했다.

| | 틀린 칸 | 놓침 | 헛것 | 코드 자기채점 |
|---|---|---|---|---|
| 눈금 없음 (예전) | **105** | 94 | 11 | 11/16 — 못 가림 |
| 눈금 있음 (지금) | **3** | 3 | 0 | 16/16 — 확정 |

35배 줄었다. 이 시험은 `sheet-readtest.html` 에 `bulge` 조건으로 넣어 두었다.
밀림 크기를 px 이 아니라 **mm 로** 적는 게 중요하다 — px 으로 두면 사진 해상도에 따라
시험 난이도가 제멋대로 바뀐다.

## 11-8. 이름이 통째로 틀렸던 이유

숫자만 틀린 게 아니었다. 종이에는 **조보규·김창범·황규철**이 인쇄되어 있는데 화면에는
**고성익·김산·박준수**가 떴다. 판독기는 인쇄된 글자를 못 읽으니, 뽑을 때 적어 둔 명단을
줄 번호로 되살리고 있었는데 — **그게 이 사진의 기록지인지 확인하지 않았다.** 마지막으로
뽑은 명단을 그냥 덮어썼다.

숫자가 맞아도 이름이 틀리면 기록은 통째로 쓸모없다. 그래서 종이 아래쪽에 **기계가 읽는
코드**를 넣었다. 날짜·경기·팀 이름을 16비트로 접어 버블로 인쇄하고(칠해진 채로 나온다),
사진에서 그 16칸을 읽어 **전부 맞을 때만** 이름을 채운다. 하나라도 어긋나면 비워 두고
사람에게 고르게 한다 — 틀리게 채우느니 안 채우는 게 낫다.

덤이 하나 더 있는데, 이게 사실 더 크다. **코드 칸은 답을 미리 아는 칸이다.** 판독기가
스스로 채점할 수 있다는 뜻이다. 앞 세 자리는 어느 기록지든 1,0,1 로 고정해 두었으므로,
그게 안 나오면 판독 위치가 어긋났다는 걸 판독기가 **혼자 알아챈다**. 그럴듯한 헛것을
내놓는 대신 못 믿겠다고 말할 근거가 짐작이 아니라 측정이 되었다.

## 11-9. 빈 기록지와 인쇄된 기록지의 좌표가 달랐다

이 설계 전체가 딛고 선 전제가 하나 있다 — "인쇄도 여기서 만들고 판독기가 쓸 좌표도
여기서 재니 둘이 어긋날 수가 없다"(`sheetform.js` 머리말). 그런데 어긋나 있었다.

판독기는 **빈 기록지**를 그려서 좌표를 재고, 사진은 **이름이 든 기록지**를 찍은 것이다.
꼬리글이 `justify-content:space-between` 으로 흘러 있어서 글자 수가 달라지면 그 안의
코드 버블이 **가로로 13.5mm** 옮겨 다녔다. 머리글도 내용에 따라 높이가 0.21mm 달라져
가운데 표(`flex:1`)가 통째로 밀렸다. 1,744칸 중 **1,423칸이 움직이고 있었다.**

머리글·꼬리글 높이를 못 박고 꼬리글 안의 것들을 자리마다 고정해서 0칸으로 만들었다.
그리고 `sheet-readtest.html` 에 **좌표 안정성 시험**을 넣었다 — 내용이 달라도 좌표가
같은지 매번 확인한다. 이 전제가 조용히 깨지면 그 밑의 모든 정교함이 무의미해진다.

## 11-10. 건별 판독 리포트

"안 맞는다"는 말만으로는 어디가 안 맞는지 알 수가 없다. 그래서 판독기가 **칸 하나하나에
대해** 무엇을 보고 그렇게 판단했는지 그대로 적어 내려주게 했다(`건별 리포트` 단추).

- 눈금 표식을 몇 개 찾았는지, 밀림 보정을 했는지
- 기록지 코드 자기채점 결과
- 어둡기 문턱값이 얼마인지
- 줄마다 무엇을 읽었는지 (사람 이름으로)
- **칠한 것으로 본 칸 전부** — `조보규 2점 전반 3번째 시도 넣음 → 검정 (어둡기 0.09)`
- **애매한 칸** — 문턱값 언저리에 있는 칸들. 틀린다면 거의 여기서 틀린다

글 복사·파일 저장도 된다. 종이를 옆에 두고 줄 단위로 대조하라고 만든 것이다.

## 11-11. 종이가 자기 명단을 들고 다닌다

11-8 에서 이름을 코드로 확인하게 고쳤지만, **이름 자체는 여전히 기록지를 뽑은 기기의
localStorage 에 있는 메모**에서 왔다. 즉 팀 편성을 한 사람과 사진을 올리는 사람이
다르면 이름이 통째로 빈칸이 된다. 동아리에서 그 둘이 같은 사람이라는 보장은 없다.
숫자는 누가 올리든 읽히는데 이름만 안 되는, 반쪽짜리였다.

그래서 이름을 **종이에 같이 찍는다**. 선수 이름 칸마다 작은 버블 일곱 개로 그 사람이
로스터 몇 번째인지 적어 둔다 — 6비트 번호 + 홀짝 검사 1비트. 인쇄할 때부터 정해져
나오는 칸이라 사람이 칠할 일은 없다.

- **0 = 빈 줄.** 로스터 번호에 1을 더해 담는다. 안 쓰는 줄에는 아무것도 안 찍혀서
  잉크도 덜 들고 종이도 덜 지저분하다.
- **홀짝 검사 1비트.** 한 칸을 잘못 읽으면 걸린다. 이름은 한 글자만 틀려도 다른
  사람이 되므로 숫자보다 더 조심해야 한다.
- **"빈 줄"과 "잘못 읽음"은 다른 값으로 돌려준다.** 처음에 이걸 섞었더니 멀쩡한
  기록지의 예비 줄이 판독 실패로 잡혔다.

이제 순서는 이렇다.

1. **종이에 찍힌 명단** — 누가 어느 기기에서 올리든 된다. 이게 기본이다.
2. **기록지 코드로 날짜·팀 확인** — 뽑은 기기에서만 되지만, 안 돼도 이름은 이미 나왔다.
3. 둘 다 있는데 **서로 다르면** 크게 알린다. 로스터 순서가 바뀐 뒤에 예전 기록지를
   올리면 이렇게 되는데, 조용히 넘어가면 엉뚱한 사람 기록이 된다.

> **로스터는 뒤에만 추가할 것.** 인쇄된 기록지가 `roster.js` 의 **순서**를 가리키고
> 있어서, 중간에 끼워 넣거나 지우면 이미 인쇄해 둔 종이가 다른 사람을 가리킨다.
> 3번 검사가 그걸 잡아 주기는 하지만, 애초에 안 흔드는 게 낫다.

`sheet-readtest.html` 의 아홉 가지 조건 전부에서 여덟 명 이름이 그대로 되살아나는지
매번 확인한다.

## 11-12. 득점까지 두 팀 통째로 맞춰 본 것

이름을 고치고 나서 "그럼 득점은?" 이라는 질문을 받았다. 득점은 버블에서 **계산**되는
값이라 판독이 맞으면 따라 맞는 게 맞지만, 말로만 그렇다고 하면 안 되니 두 팀 기록지를
정답을 알고 만들어서 앱에 통째로 넣고 결과를 대조했다.

| | 정답 | 앱이 낸 것 |
|---|---|---|
| 혼 A 총점 | 23 | **23** |
| 혼 B 총점 | 18 | **18** |
| 혼 A 쿼터(누적) | 10/14/17/23 | **10/14/17/23** |
| 혼 B 쿼터(누적) | 7/12/17/18 | **7/12/17/18** |
| TEAM MIN | 96 / 96 | **96 / 96** |
| 선수별 득점·출전분 | 10명 | **10명 전부 일치** |

쿼터 점수는 판독기가 **쿼터별**로 내고 화면·이미지는 `perQuarterToCumulative` 로
**누적**으로 바꿔 보여준다 — 종이 위 손글씨 표가 "그때까지의 누적 점수"라서 기준을
맞춰 둔 것이다. 종이와 화면을 나란히 놓고 대조할 수 있다.

MIN 은 `출전 쿼터 수 × 8분`이다. 예전에 TEAM MIN 이 72 대 32 로 터무니없이 기울어
보였던 건 **출전 열이 통째로 밀려 읽히던 것**의 그림자였고, 정렬을 고치니 같이 맞았다.

### 곁다리로 잡은 두 가지

- **Play 줄에 등번호와 이름이 섞여 있었다.** `26 4 권혁남 47` — 47 이 사람인지 번호인지
  알 수가 없다. 등번호에 `#` 을 붙여 `#26 #4 권혁남` 으로 바꿨다. 등번호 없는 선수가
  하나(권혁남) 있는 한 이건 계속 문제가 된다.
- **사진이 아닌 걸로 판단되면 조용히 버리고 있었다.** 안드로이드 공유나 일부 파일
  관리자는 사진을 `application/octet-stream` 이나 빈 문자열로 넘긴다. 그러면 걸러져서
  **아무 일도 안 일어난 것처럼** 보인다. 확장자로도 한 번 더 보고, 그래도 못 받으면
  이유를 말하게 했다.

## 11-13. 아이폰에서 인쇄하면 오른쪽이 잘렸다

11-6 에서 `@page{size:297mm 210mm}` 로 A4 가로를 잡았고 크롬 데스크톱 PDF 로
297.0 × 209.9mm 를 확인했다. 그런데 아이폰에서 뽑은 PDF 를 받아 보니 **210 × 297mm
세로**였고 기록지 오른쪽 87mm 가 통째로 잘려 있었다.

```
Producer: iOS Version 26.6 (Build 23G71)
Creator:  Safari
MediaBox: [0 0 595.28 841.89] -> 210.0 x 297.0 mm
```

**iOS 사파리는 `@page` 의 `size` 를 아예 보지 않는다.** 데스크톱 크롬에서만 시험한
것이 화근이었다 — 정작 종이를 뽑는 곳은 휴대폰인데.

### 고친 방법 — @page 에 안 기댄다

세로 A4 는 어디서나 기본값이라 브라우저 지원을 안 탄다. 그래서 **세로 A4 면 안에서
기록지를 90° 돌려** 찍는다. 나온 종이를 옆으로 돌려 쓰면 된다 — 폭 넓은 서식은
원래 그렇게 뽑는다.

```css
@page{size:A4 portrait;margin:0}
.sheet-page{width:210mm;height:297mm;position:relative}
.sheet-page .sheet{position:absolute;top:0;left:0;width:297mm;height:210mm;
  transform:translateX(210mm) rotate(90deg);transform-origin:top left}
```

좌상단을 축으로 90° 돌리면 x 가 −210~0 으로 가므로 210mm 만큼 오른쪽으로 민다.
결과가 정확히 210×297 을 채운다.

### 확인 방법

**데스크톱 크롬의 `preferCSSPageSize:true` 로 재면 안 된다** — 그건 `@page` 를
존중하는 쪽이라 아이폰에서 벌어지는 일을 못 본다. `@page` 를 무시하는 상황을
그대로 흉내내야 한다:

```js
await page.pdf({format:"A4", landscape:false, printBackground:true, margin:{...0}})
```

이렇게 뽑아서 잰 결과 — 면 210×297mm, 기록지 상자도 210×297mm, 좌상단 오프셋 0,0,
오른쪽·아래 넘침 0. 두 팀이면 두 면이 정확히 297mm 간격으로 떨어진다.

## 11-14. 안내문이 인쇄 단추를 화면 밖으로 밀어냈다

고칠 때마다 인쇄 모달 안내문에 한 줄씩 덧붙였다. 배경 그래픽, 용지 방향, 눈금 표식,
이름 칸… 하나씩 보면 다 맞는 말인데 쌓이니 **380자짜리 벽**이 됐다. 아이폰에서 재 보니
안내문만 336px 이고 모달 전체가 1006px 인데 화면은 844px — **인쇄 단추가 862px 자리에
있어 아예 누를 수가 없었다.**

기능을 고치면서 그 설명을 같은 자리에 계속 붙이면 이렇게 된다. 설명이 늘어난 만큼
정작 그 화면이 하려던 일(인쇄)이 밀려난다.

### 고친 것

- 안내는 **인쇄 창에서 실제로 눌러야 하는 것**만 남겼다 — 배경 그래픽 켜기 · 배율 100% ·
  여백 없음 · 용지 A4 세로. 380자 → 62자.
- 나머지 설명은 `왜 이렇게 하나요?` 로 접었다. 매번 읽을 것이 아니라 한 번 궁금할 때
  펴 보는 것이다.
- 모달을 `max-height:92vh` 로 화면에 가두고 **미리보기만** 늘었다 줄었다 하게 했다
  (`flex:1 1 auto; min-height:120px`). 이제 인쇄 단추가 밖으로 밀려날 수가 없다.
- 미리보기 축소 비율을 **상자 폭을 재서** 정한다. 0.34 로 고정해 뒀더니 좁은 화면에서
  기록지 오른쪽 열이 상자 밖으로 나가 안 보였다 — 미리보기인데 못 보면 소용이 없다.

| 화면 폭 | 축소 비율 | 기록지 / 상자 | 가로 잘림 | 인쇄 단추 |
|---|---|---|---|---|
| 390px | 0.258 | 290 / 310 | 0 | 보임 |
| 430px | 0.294 | 330 / 350 | 0 | 보임 |
| 768px | 0.595 | 668 / 688 | 0 | 보임 |
| 1280px | 0.800 | 1040 / 1060 | 0 | 보임 |

## 11-15. 세로 A4 를 꽉 채웠더니 2장이 4페이지가 됐다

11-13 에서 세로 A4 에 90° 돌려 넣으면서 **정확히 210×297 을 채우게** 했다. 잰 값도
넘침 0 이었다. 그런데 아이폰 인쇄 화면을 보니 기록지 2장이 **4페이지**로 잡혔고
2·4면은 거의 백지였다 — 매 장마다 자투리가 다음 면으로 넘어간 것이다.

종이가 210×297 이어도 **실제로 찍히는 영역은 그보다 작다.** iOS 사파리는 위아래에
주소·날짜·쪽번호를 넣고(끌 수도 없다), 프린터마다 물리적 여백도 있다. 딱 맞춘 게
화근이었다.

### 고친 것

기록지를 `FIT = 0.85` 로 줄여 앉힌다. 178.5 × 252.5mm 라 A4 에서 위아래 44mm,
좌우 31mm 가 남는다. 균일 축소라 판독은 영향받지 않는다 — 판독기는 표식 네 점으로
좌표를 다시 잡으므로 종이가 몇 % 작아도 그대로 읽는다.

상자는 기록지보다 **0.6mm 크게** 잡는다. 딱 맞추면 반올림으로 0.1mm 가 밖으로
나가는데, 그렇다고 `overflow:hidden` 으로 잘라내면 **맨 아래 눈금 표식 줄이 잘린다.**
표식이 잘리면 판독이 통째로 망가지므로 자르지 않고 여유를 준다.

### 시험이 거짓말을 했다 — 적어 둔다

처음엔 `page.pdf({format:"A4", margin:{top:"12mm",...}})` 로 여백을 준 PDF 를 뽑아
페이지 수를 셌다. **줄이기 전(FIT=1.0)에도 2페이지가 나왔다.** 크로미움의 `pdf()` 는
여백을 주면 내용을 그 안에 **맞춰 줄여** 버리고, 아이폰처럼 넘겨 버리지 않는다.
즉 그 시험은 아무것도 검증하지 못하고 있었다.

시험이 고장을 못 잡는지부터 확인할 것. **일부러 망가뜨렸을 때 빨간불이 켜져야**
그 시험을 믿을 수 있다. 여기서는 대신 인쇄 시점의 상자 크기를 mm 로 직접 재고,
A4 에서 얼마가 남는지를 본다:

| | 값 |
|---|---|
| 상자 | 179.1 × 253.0mm |
| 기록지 | 178.5 × 252.4mm |
| 넘침 | −0.6 / −0.6mm (안쪽) |
| A4 여유 | 좌우 30.9mm · 위아래 44.0mm |

## 11-16. 비고를 줄이고 그만큼을 버블 간격에 줬다

비고는 "칸이 모자랄 때 몇 자 적는" 자리다. 기록 자체에 들어가지도 않고 판독기는
어차피 손글씨를 못 읽는다. 21mm → **11.6mm** 로 줄여 9.4mm 를 얻었다.

열 폭도 손으로 적어 두던 것("53.0mm 35.7mm …")을 **버블 크기와 간격에서 계산**하게
바꿨다. 손으로 적어 두면 버블을 조금만 건드려도 칸이 안 맞아 넘치거나 남는다.

```js
const shotW = (n) => n*(BUB.w + ATT.pad*2) + (n-1)*ATT.gap
                   + Math.floor(n/5)*ATT.group + HALF_PAD*2;
const cntW  = (w) => w*BUB.w + (w-1)*CNT_GAP + CNT_PAD*2;
```

얻은 9.4mm 는 **버블 사이 간격**에 얹었다(슛 0.40→0.65mm, 카운트 0.70→0.94mm).
가로 간격 4.10 → **4.34mm**. 버블 자체는 3.2mm 그대로 뒀다.

### 왜 버블을 키우지 않았나

3.2 → 3.4mm 도 해 봤다. 표본이 인쇄된 테두리에 가까워지면서 빈 칸 기준이 어두워지고,
마킹의 상대 어둡기가 문턱값 언저리로 밀려 올라갔다. 간격을 넓히는 쪽은 그런 부작용이
없고, 판독이 어긋날 때는 늘 **옆 칸을 건드릴 때**였으므로 여유가 커지는 편이 낫다.

버블을 키운 뒤에는 표본 반경도 0.45 → **0.36** 으로 좁혔다. 사람들이 칠하는 모양은
칸을 꽉 채우는 덩어리라 가운데가 가장 확실하고, 테두리에서 멀수록 안전하다.
간격만 넓힌 최종 배치에서도 0.36 이 가장 좋았다(readtest 9/9, 0.40·0.45 는 8/9).

### 시험이 배치 비교에는 못 쓴다 — 알아 두고 쓸 것

`score.mjs` 로 배치들을 비교하려 했는데 숫자가 이상했다.

| 배치 | 평균 틀린 칸(1,792 중) |
|---|---|
| 원래 (비고 21mm) | 1.4 |
| 간격 넓힘 | 4.4 |
| 버블 키움 | 5.0 |
| **버블 배치는 원래 그대로**, 비고만 줄이고 이름·라벨 칸을 넓힘 | 3.8 |

마지막 줄이 핵심이다. **버블 간격이 원래와 똑같은데도** 점수가 달랐다. 격자가 통째로
옆으로 밀리면 "어느 버블이 하필 많이 밀린 자리에 놓이는가"가 바뀌기 때문이다.
왜곡을 다섯 개로 늘려 평균을 내도 다섯 개가 전부 페이지 좌표의 매끄러운 함수라
같이 움직인다.

즉 이 시험은 **몇 칸 차이로 배치를 비교할 수 없다.** 확실히 말해 주는 건 큰 신호뿐이다
— 눈금 표식 있음 4.4 vs 없음 82. 그래서 배치는 벤치마크가 아니라 물리적 근거로 정했다.

## 11-17. 아이폰이 실제로 찍는 세로는 248.6mm 다 — 재서 알아냈다

11-15 에서 0.85 로 줄였는데도 여전히 2장이 4페이지로 나왔다. "업데이트가 안 된 거냐"는
말을 들었는데, **적용은 되어 있었다.** 어제 PDF 와 오늘 PDF 를 열어 그려진 범위를
비교하니 폭이 198.1 → 181.8mm 로 줄어 있었다. 줄이긴 줄였는데 **덜 줄인 것**이었다.

### 재는 방법

아이폰에서 뽑은 PDF 를 pymupdf 로 열어 쪽마다 그려진 내용의 시작 y 를 본다.

```python
import pymupdf
d = pymupdf.open("Spirit.pdf")
for pg in d:
    r = [x["rect"] for x in pg.get_drawings()]
    print(min(v.y0 for v in r) * 25.4/72)   # mm
```

나온 값: `14.2, -234.5, -483.1, -731.7`. 차이가 **248.7 / 248.6 / 248.6mm**.
즉 iOS 사파리가 실제로 찍는 세로는 **248.6mm** 다(A4 297mm 중 48mm 를 머리글·바닥글과
여백이 먹는다). 가로는 내용이 x=14.1 에서 181.8mm 이므로 **181.8mm**.

0.85 일 때 상자가 297×0.85+0.6 = **253.0mm** 였으니 **딱 4.4mm 초과**. 매 장 그만큼이
다음 면으로 넘어가 2장이 4페이지가 됐다.

### 고친 것

`FIT = 0.78` → 상자 232.3mm. 세로 여유 16.3mm, 가로 여유 17.4mm.

이제 이 숫자를 **시험이 지킨다** — 상자가 248.6×181.8mm 를 넘으면 실패로 잡는다.
추측으로 다시 조이지 말고, 고칠 일이 생기면 같은 방법으로 실물 PDF 를 다시 잴 것.

## 11-18. 미리보기를 "무엇이 찍히나"로 바꿨다

인쇄 모달에 기록지를 통째로 줄여 보여주고 있었다. 그런데 390px 휴대폰에서 한 장이
**290×205px** — 우표만 해서 아무것도 안 읽힌다. "짜부되어 있어서 큰 의미가 있나"라는
말을 들었고, 맞는 말이다.

인쇄 직전에 정작 확인해야 하는 건 기록지가 어떻게 생겼는지가 아니라
**누가 어느 팀 종이에 찍히는가** 다. 그건 글로 보여주면 다 읽힌다.

- 팀마다 한 줄: 팀 이름 · 인원 · `#26 고성익 · #7 김성훈 · …`
- 날짜·경기 번호 한 줄
- 기록지 그림은 `기록지 모양 보기` 로 **접어 뒀다**

접었을 때 모달이 1006px → **548px**. 인쇄 단추가 화면 안에 넉넉히 들어온다.

접힌 미리보기는 화면에서 `display:none` 인데, **인쇄 CSS 가 이를 무시하고 다시 편다.**
안 그러면 접어 둔 채로 인쇄했을 때 백지가 나온다 — 접기와 인쇄는 별개여야 한다.

```css
.sheet-print-preview,.sheet-print-preview.is-folded{
  display:block!important;visibility:visible!important;height:auto!important}
```

접은 채로 뽑아 2쪽·각 장 온전함을 확인했다.

## 11-19. 초점 나간 표식 하나가 기록지 한 장을 통째로 망쳤다

실전 사진 두 장(IMG_2182 · IMG_2183)이 "엉망이야 읽지를 못해" 소리를 들었다. 재 보니
2182 는 칠해진 칸을 **53개**로 봤다. 사람 눈으로 세면 120개가 넘는 종이다.

원인을 끝까지 따라갔다.

1. 판독기가 왼쪽 아래 **귀퉁이 표식을 못 찾고**, 그 위에 있는 눈금 표식을 귀퉁이로 집었다.
2. 왜 못 찾았나 — 덩어리 목록에 아예 없었다.
3. 왜 없었나 — 걸러졌다. `fill > 0.62` 에서.

그 표식만 **초점이 나가 찍혔다**. 파이썬으로 그 자리를 직접 훑어 재 보니
`n=2974, 바깥 네모 79×70, 채움률 0.538` 이었다. 표식 자체는 55×55 쯤인데, 번진 꼬리가
바깥 네모를 79×70 으로 부풀렸다. 넓이는 그대로인데 네모만 커졌으니 채움률이 떨어진다.
표식은 멀쩡히 새까맣다(평균 밝기 16). **흐릿하다는 이유만으로 사라진 것이다.**

### 고친 방법 — 바깥 네모 대신 퍼진 정도

크기와 모양을 바깥 네모(min/max)로 재는 걸 그만뒀다. 대신 덩어리를 이루는 점들의
**좌표 분산**으로 잰다. 속이 꽉 찬 정사각형은 좌표의 표준편차가 한 변의 `1/√12` 이므로

```
ex = √(12·Var(x))     ey = √(12·Var(y))     solid = n / (ex·ey)
```

`solid` 는 꽉 찬 네모면 1.0, 원이면 1.05, **속 빈 동그라미(버블 테두리)면 0.2 근처**다.
바깥 네모와 달리 가느다란 꼬리 몇 점에는 거의 흔들리지 않는다. 흐릿해도 정사각형은
정사각형이다.

걸러내는 조건: `0.6 < ex/ey < 1.7` 이고 `0.7 < solid < 1.4`.

### 같이 고친 것 세 가지

표식 하나를 찾는 문제 말고도, 이번에 같이 재서 고친 게 있다.

- **귀퉁이 후보를 하나만 고르지 않는다.** 귀퉁이마다 후보를 넷씩 두고, 조합마다
  호모그래피를 풀어 **눈금 표식을 가장 많이 설명하는 조합**을 고른다. 종이가 답을
  들고 있으니 그걸로 채점하면 된다.
- **스냅 범위를 줄 간격에 맞췄다.** 예전엔 버블 세로 반지름의 0.35 (=3.6px) 였는데,
  눈금 보정을 다 하고도 실제로 남는 밀림이 ±9px 이라 손도 못 대고 있었다. 이제
  같은 열 버블의 세로 간격(`rowPitchPx`)을 재서 그 0.38 까지 찾는다. 0.5 미만이어야
  옆 줄에 안 닿는다.
- **이름 칸(`r:`)도 스냅 표본에 넣었다.** 빼 놓으니 표 왼쪽 끝에 표본이 없어서
  그 근처 보정이 바깥값으로 밀려났다.

| 2182 눈금 표식 | 28/38 | 37/38 | **38/38** |
| 2182 칠해진 칸 | 53 | 67 | **125** |

`sheet-readtest.html` 의 `__blobShape()` 는 **그때 잰 그 덩어리를 그대로 재현한다** —

### 아직 남은 것

두 장 다 **맨 위 두 줄의 이름 칸을 못 읽는다.** 눈금 보정을 다 하고도 그 근처에
세로로 10px 쯤이 남는데, 이름 칸 버블은 2.1×1.9mm 로 작아서 그만큼이면 빗나간다.
스냅 범위를 줄 간격의 0.38 → 0.48 로 넓히면 숫자는 더 잡히지만(2182 125→132)
옆 줄을 잘못 집을 위험이 같이 커져서 **손대지 않았다.** 제대로 고치려면 이름 칸
버블을 다른 칸과 같은 크기로 키워야 한다.

대신 **틀린 걸 틀렸다고 말하게** 했다. 이름 칸은 일곱 비트 중 하나가 홀짝 검사라
판독기가 스스로 채점할 수 있는 유일한 칸이다.

- 홀짝 검사에 걸린 줄이 있으면 → 그 줄 수를 말한다
- **기록은 있는데 이름 칸이 비어 나온 줄**이 있으면 → 그 줄은 빗나간 것이다
  (예비 줄에는 기록이 없다. 그래서 이 둘은 구별된다)

두 사진 다 이제 "3줄이 빗나갔다"고 스스로 말한다. 조용히 틀린 숫자를 보여주는 것보다는
낫다.

## 11-20. 비고 칸을 줄였더니 이미 인쇄한 종이가 전부 어긋났다

11-19 를 고치고 나서도 실제 사진의 **맨 위 두 줄**만 계속 안 맞았다. 원인을 짐작하지
않고 잔차를 그려 봤다.

먼저 네 변의 눈금 표식 잔차부터 쟀다 — 예상 자리와 실제 자리의 차이다.

```
2182  l: +0.7,+0.5  +0.7,+0.4  +1,+0.8 …  (가장 큰 게 5px)
```

**가장자리는 멀쩡했다.** 그러면 밀린 건 종이 가장자리가 아니라 표 안쪽이다.

그래서 선수 줄마다 세로 밀림을 넓게(±30px) 찾아봤다.

```
2182  줄0 -19   줄1 -16   줄2 -15   줄3 -13   줄4 -12  …  줄8 -3
2183  줄0 -17   줄1 -15   줄2 -13   …                      줄8 -5
```

두 사진이 **똑같은 모양의 기울어진 밀림**이었다. 잡음이 아니다.

### 범인은 내가 지난주에 만든 것이었다

표의 짙은 머리띠가 종이 몇 mm 자리에 있는지, 사진과 코드에서 **같은 방법으로** 쟀다.

| | 위 | 아래 | 높이 |
|---|---|---|---|
| 사진 속 인쇄물 | 28.8mm | 37.2mm | 8.4mm |
| 지금 코드 | 28.3mm | **39.4mm** | **11.1mm** |
| 11-16(비고 줄이기) 직전 코드 | 28.3mm | 36.7mm | 8.4mm |

11-16 에서 비고를 21mm → 11.6mm 로 줄였다. 그러자 머리띠의 작은 글씨
**"칸 모자랄 때"가 두 줄로 접혔고**, 머리띠가 2.7mm 자랐다. 표 아래쪽은 꼬리글에
묶여 있으니 자란 만큼이 선수 줄 아홉 개로 퍼졌다 — 맨 위 2.7mm(19px), 맨 아래 0.
잰 잔차와 정확히 같은 모양이다.

**가로 폭을 줄였는데 세로가 밀렸다.** 그리고 그날 이후로 뽑은 종이와 그 전에 뽑은
종이는 서로 다른 물건이 됐다.

### 왜 시험이 못 잡았나

`__geomStability()` 는 "같은 날 그린 두 기록지가 서로 같은가"를 본다. 이 사고는
**둘 다 똑같이 틀린** 경우라 절대 안 걸린다. 판독 시험 9종도 마찬가지다 — 그리는
쪽과 읽는 쪽이 같은 코드라 언제나 맞는다. 종이는 **인쇄한 날과 읽는 날 사이에**
어긋나는데, 그 축을 재는 시험이 하나도 없었다.

### 고친 것

1. **머리띠 높이를 숫자로 못 박았다** — `height:8.4mm`, 작은 글씨는 `nowrap`.
   이제 무슨 글자를 넣든 표가 안 움직인다. ("칸 모자랄 때" → "메모" 로 줄여 안 잘리게 했다.)
2. **아무하고도 견주지 않는 시험을 넣었다.** `__geomAnchor()` 는 머리띠 위/아래,
   첫 줄 시작, 줄 높이, 표 끝을 **정해둔 mm 값**과 견준다.
   ```
   { headTop: 28.26, headBot: 36.66, row0: 36.66, rowH: 17.63, tableBot: 195.35 }
   ```
   이 값이 달라지면 시험이 빨간불을 켠다. 값을 고치는 건 "이미 인쇄된 종이를 전부
   버린다"는 뜻이므로, 고치기 전에 반드시 멈춰야 한다.
3. 못 박은 높이를 **11-16 이전 값(8.4mm)** 으로 잡았다. 그래서 이미 뽑아 둔 종이가
   다시 맞는다 — 새로 인쇄할 필요가 없다.

### 이름 칸은 문턱값이 문제였다

자리가 맞고 나니 이름 칸의 진짜 문제가 드러났다. 이 칸들은 사람이 칠하는 게 아니라
**인쇄되어** 나오고, 2.1×1.9mm 로 작아서 손마킹(어둡기 0.1~0.3)만큼 진하지 않다 —
0.45~0.75 쯤이다. 그런데 문턱값은 손마킹 기준으로 0.63 에 잡히니 인쇄된 칸 무리
한가운데를 갈라 버렸다. 조보규 줄이 `0.64 / 0.53 / 0.54 / 0.47` 이었는데 0.64 하나만
문턱을 넘겨 홀짝 검사에서 걸렸다.

그래서 이름 칸은 **그 줄 안의 명암 차이로만** 가른다(`rowBitsByContrast`). 일곱 개를
정렬해 가장 큰 틈에서 자르되, 틈이 0.3 보다 좁거나 어두운 쪽이 0.85 보다 밝으면
포기하고 원래 문턱값으로 돌아간다. 마지막에 홀짝 검사가 한 번 더 거른다.

## 11-21. 한 군데 어긋났다고 140개를 손으로 치게 만들고 있었다

기록지 판독을 시험해 보려던 사람이 **손으로 선수를 하나씩 추가하며 숫자를 치고
있었다.** "개 노가다"라는 말을 들었고, 맞는 말이다. 사진을 올리면 다 읽어 놓고서
왜 그러고 있었나 봤더니, 코드에 이 한 줄이 있었다.

```js
if (sh.judge && !sh.judge.ok) { skipped++; continue; }
```

"못 믿을 판독은 조용히 보여주지 않는다"는 뜻으로 넣은 것이다. 의도는 맞았는데
결과가 틀렸다. **한 군데 어긋났다는 이유로 나머지 139개까지 같이 버렸고**, 사람은
그걸 처음부터 다시 쳤다. 그건 도구가 아니라 벌이다.

바꿨다. 읽은 건 다 넣고, 못 믿을 이유를 크게 붙인다.

- 판정에 걸린 기록지도 **넣는다.** 대신 `⚠ N장은 판독이 미덥지 않습니다 —
  「건별 리포트」를 열어 종이와 맞춰보고 고쳐주세요` 를 붙인다.
- 이름을 못 읽은 줄은 **골라만 주면 그 줄 숫자가 같이 들어간다.** 그 줄을 눈에 띄게
  칠하고 위에 안내를 단다: "숫자는 다시 안 치셔도 됩니다."

다섯 개 고치는 게 140개 치는 것보다 언제나 낫다.

### 덤으로 잡은 것 — 용원식을 손걸로 읽고 있었다

그 사람이 올린 화면 사진에 종이의 진짜 명단이 찍혀 있었다. 공짜로 얻은 정답지다.
맞춰 보니 **2183 의 셋째 줄을 용원식이 아니라 손걸로 읽고 있었다.**

원인이 둘이었다.

**① 절대 밝기로 거른 것.** 11-20 에서 "어두운 쪽이 0.85 보다 밝으면 포기"를 넣었는데,
그 줄만 인쇄가 연하면(어두운 쪽 0.92, 밝은 쪽 1.93 — 차이는 두 배인데 둘 다 밝다)
멀쩡히 읽을 수 있는 줄을 버렸다. 그러고는 **손마킹용 문턱값으로 되돌아가** 두 자리를
틀리게 읽었다. 홀짝 검사는 틀린 자리가 짝수 개면 그냥 통과한다 — 그래서 엉뚱한
이름이 아무 경고 없이 나왔다.

→ 되돌아가는 길을 **없앴다.** 못 읽으면 못 읽었다고 한다. 그리고 밝기 자체가 아니라
**몇 배 벌어졌는지**(`lightMin / darkMax ≥ 1.35`)만 본다.

**② 자를 자리를 "차이가 가장 큰 곳"으로 잡은 것.** 밝은 쪽은 꼬리가 길다 — 이웃이
어두운 칸은 어둡기가 2.8 까지 간다. 그래서

```
0.07  0.07  0.07  0.07  1.11  2.81  2.81
                          ↑차 1.04    ↑차 1.70  ← 여기를 골랐다
```

어두운 칸 넷에 1.11 을 얹어 홀짝 검사를 깨뜨렸다. **몇 배**로 재면 0.07→1.11 이
15.9배로 압도적이라 제대로 잘린다. 인쇄가 진하든 연하든 똑같이 동작한다.

## 11-22. 빨강 펜이 문턱값에 매달려 있었다

실전 기록지 두 장(혼 A · 혼 B)과 판독 리포트를 받았다. 리포트만 보고도 잡히는 게 있었다.

### ① 종이를 안 보고 알 수 있는 모순

혼 A 의 세 줄이 **출전 쿼터는 1쿼터뿐인데 후반(3·4쿼터) 슛 기록이 있었다.**

```
배준혁  출전 1  ·  2점 후반 1~6번째, 자유투 후반 1~4번째, 3점 후반 1·2번째
조보규  출전 1  ·  2점 후반 1·2번째, 자유투 후반 1·2번째
이남희  출전 1  ·  2점 후반 1~4번째, 자유투 후반 1~4번째
```

1쿼터만 뛴 사람이 후반에 슛을 쐈을 수는 없다. **종이를 한 번도 안 보고** 판독이
틀렸다고 단정할 수 있는 종류의 증거다. 그리고 "애매한 칸" 목록에 답이 있었다 —
`조보규 출전 2쿼터 → 빈 칸 (0.645)`, `배준혁 출전 4쿼터 → 빈 칸 (0.687)`.

### ② 빨강이 문턱값에 매달려 있었다

리포트의 어둡기를 색깔별로 갈라서 재 봤다.

| | 개수 | 중앙값 | 가장 연한 것 |
|---|---|---|---|
| 검정 마킹 | 136 | 0.138 | 0.607 |
| **빨강 마킹** | 32 | **0.535** | **0.613** |
| 빈 칸 | — | — | 가장 어두운 것 **0.636** |

문턱값이 **0.62**. 통과한 빨강 중 가장 연한 것(0.613)과 빈 칸 중 가장 어두운 것
(0.636) 사이가 **0.021** 이었다. 그 틈에 걸린 빨강은 이미 몇 개씩 떨어지고 있었다.

원인은 명확하다. 어둡기를 **휘도**로 쟀는데, 휘도는 빨강 채널에 0.299 를 준다.
빨강 펜은 R 이 그대로 밝게 남으므로 검정보다 훨씬 연하게 잰다. 그런데 **빨강은
짝수 쿼터를 뜻한다** — 떨어지면 2·4쿼터 기록이 통째로 사라진다.

### 고친 것 — 채널마다 따로 재기

먼저 `min(R,G,B)` 로 바꿔 봤다. 빨강은 좋아졌는데 **합성 시험 아홉 중 둘이 깨졌다** —
출전 칸처럼 옅게 깔린 바탕에서는 그 색 때문에 기준이 통째로 내려앉아, 멀쩡히 칠한
칸이 상대적으로 연해 보였다.

그래서 **채널마다 기준을 따로 잡고** 각 채널의 "종이 대비 어둡기"를 구한 뒤
그중 가장 작은 값을 쓴다. 바탕색은 채널 안에서 상쇄된다.

```js
it.ratio = Math.min(...[0,1,2].map((k) => it.rgb[k] / ref[k]));
```

| | 전 | 후 |
|---|---|---|
| 빨강 중앙값 (혼 A) | 0.535 | **0.371** |
| 빨강 중앙값 (혼 B) | 0.503 | **0.318** |
| 빈 칸 중 가장 어두운 것 (혼 A) | 0.636 | **0.706** |
| 빈 칸 중 가장 어두운 것 (혼 B) | 0.636 | **0.841** |
| 잡아낸 빨강 개수 | 32 · 30 | **42 · 35** |

①의 모순도 같이 사라졌다 — 조보규 1,2,4 · 이남희 1,2,3 으로 출전이 채워졌다.

### ③ "손걸 함정"

어둡기 눈금이 바뀌자 이름 칸 판별이 흔들렸다. 파고들어 보니 진짜 문제는 따로 있었다.

**손걸은 로스터 15번이라 코드가 `0000101` — 어두운 칸이 둘뿐이다.** 그래서 어느
줄이든 **너무 바싹 자르면** 가장 어두운 두 칸만 남아 손걸이 튀어나온다. 홀짝 검사도
통과한다. 실제로 심인보·용원식·이찬희 세 줄이 전부 손걸로 읽힐 뻔했다.

```
용원식 줄  0.23  0.57  0.73  0.82  1.01  2.36  2.59
           └0.23 뒤에서 자르면(x2.48) → 홀짝 실패
                 └0.57 뒤에서(x1.28) → 0000101 = 손걸   ← 함정
                             └0.82 뒤에서(x1.23) → 0110101 = 용원식  ← 정답
```

"가장 많이 벌어진 곳에서 자른다"로는 손걸이 이긴다. 그래서:

1. 자를 만한 자리를 **전부** 시험한다(1.2배 이상 벌어지고, 어두운 쪽이 0.9 미만).
2. 홀짝 검사를 통과하고 **명단에 실제로 있는** 답만 남긴다.
3. 그래도 여럿이면 **어두운 칸이 가장 많은 답**을 고른다.

3번이 왜 맞나 — 너무 바싹 자르면 진짜 어두운 칸을 **잃기만** 하지 없던 칸이 생기진
않는다. 그러니 남은 답들은 정답의 부분집합이고, 가장 큰 것이 정답이다. 개수가 같아
가릴 수 없으면 포기한다.

|---|---|---|
| 혼 A 이름 | 6명 ✓ | **6명 ✓** |
| 혼 B 이름 | 5명 · **손걸 오독** | **6명 ✓ · 오독 0** (1줄은 못 읽고 그렇다고 말함) |

가를 수 없다.** 이건 판독기가 아니라 그 줄의 인쇄 문제다. 못 읽었다고 말하고 사람이
고르게 둔다.

### 남은 위험 — 정답지가 없다

여기까지는 전부 **종이를 안 보고** 잡을 수 있는 것들이었다: 모순, 색깔별 분포,
코드의 홀짝 검사. 하지만 "2점 5/10 이 맞나"는 이 방법으로 못 잰다. 사진을 눈으로
세어 정답지를 만들면 **그 정답지 자체가 틀린다** — 그러면 틀린 자를 들고 자를
고치는 셈이 된다. 숫자 정확도는 사람이 종이를 보고 확인해 주기 전까지 미지수다.

## 11-23. 처음으로 진짜 정답지가 생겼다

혼 A 기록지의 조보규 줄을 **사람이 종이를 직접 보고 한 칸씩 확인해 줬다.** 전부 맞았다.

```
출전 1,2,4 · 2점 5/10 · 3점 2/4 · 자유투 1/2
리바 4 어시 4 스틸 2 블락 1 턴오버 1 파울 1
```

이게 이 프로젝트에서 **처음 생긴 진짜 정답**이다. 그동안의 시험은 전부 그리는 쪽과
읽는 쪽이 같은 코드라 언제나 맞았고(11-20 참고), 실제 사진에 대해서는 "칠해진 칸이
늘었다" 같은 대리 지표만 봤다. 종이·프린터·펜·카메라가 끼어드는 진짜 오차는 거기서
나오지 않는다.

### 왜 눈으로 세면 안 되나

판독기를 사진에 맞춰 고치려면 정답이 필요한데, 사진을 눈으로 세어 정답을 만들면
**그 정답이 먼저 틀린다.** 틀린 자를 들고 자를 고치는 셈이라, 맞춰 갈수록 더
멀어진다. 그래서 이 값은 반드시 사람이 종이를 보고 준 것이어야 한다.

### 붙박이로 만들어 뒀다

- `test/fixtures/sheet-honA-260823.jpg` — 그 사진을 앱과 같은 2200px 로 줄인 것(834KB)
- `tools/real-photo-check.mjs` — 그 사진을 읽어 위 열세 개 값과 대조한다

한 줄이지만 얇지 않다. 그 줄 하나에 200칸쯤 들어 있고, **검정·빨강 마킹이 섞여 있고**,
출전·슛·카운트 세 종류가 다 들어 있다. 빨강이 섞여 있다는 게 특히 중요하다 — 11-22
에서 고친 게 바로 빨강이 문턱값에 매달려 있던 문제였다.

시험이 실제로 잡는지도 확인했다. 기대값의 `p2m` 을 5→6 으로 한 칸만 틀리게 두고
돌리니 `p2m 기대 6 · 실제 5` 로 잡아내고 종료코드 1 을 냈다.

**기대값을 고치지 말 것.** 종이가 그렇게 칠해져 있다.

## 11-24. 문턱값이 골짜기가 아니라 바닥에 붙어 있었다

박윤호 줄도 사람이 종이를 보고 확인해 줬다. **3점만 틀렸다** — 판독기가 `0/2`,
종이는 `1/3`. 넣음 칸 하나를 통째로 놓친 모양이다(넣음을 놓치면 시도와 성공이
같이 하나씩 준다).

그 칸을 찾았다. **3점 전반 2번째 넣음, 어둡기 0.694.** 문턱값은 0.62 였다.

### 분포를 그려 보니 문턱값이 엉뚱한 데 있었다

```
혼A  마킹 0.30~0.62 …… 0.694  0.782 …… 골짜기 …… 0.89~1.05 (빈 칸 1,540개)
                          ↑떨어진 칸        ↑문턱값이 있어야 할 자리
     ↑ 문턱값 0.62 가 여기 있었다
```

혼 A 의 실제 골짜기는 **0.782~0.889**, 혼 B 는 **0.597~0.837** 이었다. 문턱값
0.62 는 골짜기가 아니라 **마킹 무리의 꼬리**에 앉아 있었다. 빈 칸 무리에서 0.2 나
떨어진 칸을 빈 칸이라고 부르고 있었던 것이다.

원인은 `Math.max(0.62, Math.min(otsuOn(ratios), 0.90))` 의 **0.62 바닥**이다.
빈 칸이 1,550개 대 마킹 180개로 압도적이고 빈 칸 무리가 아주 좁게 뭉쳐 있어서,
오츠가 자꾸 아래쪽을 갈라 바닥에 붙었다. 그 바닥이 그대로 문턱값이 됐다.

### 고친 것 — 골짜기를 직접 찾는다

`valleyCut()`: 어둡기를 정렬해 **중앙값 아래에서 가장 넓은 빈 구간**을 찾고
그 한가운데를 쓴다. 골짜기가 0.10 보다 좁으면(마킹이 없거나 흐린 것이 이어져
있으면) 예전 방식으로 돌아간다.

문턱값이 이제 사진마다 다르게 나온다 — 예전엔 죄다 0.62 바닥이었다.

```
혼A 0.835   혼B 0.717   합성 9종 0.480~0.689
```

### 잰 결과

| | 전 | 후 |
|---|---|---|
| **박윤호 3점** | 0/2 ❌ | **1/3 ✅** (사람이 확인한 값) |
| 조보규 열세 칸 | ✅ | ✅ |
| 합성 시험 9종 | 9/9 | 9/9 · 어긋남 0 |

**새로 잡힌 칸은 정확히 둘이었다.** 하나는 박윤호의 그 3점(정답), 다른 하나는
예비 줄의 3점 칸(어둡기 0.782)이다. 잘라서 확대해 보니 **잉크가 실제로 있다** —
꽉 칠한 게 아니라 펜이 스친 자국이다. 판독기가 잉크를 잉크라고 부른 것이라
틀렸다고 하기 어렵고, 예비 줄은 이름이 없어서 `applySheets()` 가 어차피 안 넣는다.
숫자를 망치지 않는다.

### 붙박이 시험이 두 줄이 됐다

`tools/real-photo-check.mjs` 가 이제 조보규·박윤호 **두 줄**을 대조한다.
스물여섯 개 값이다. 기대값은 여전히 사람이 종이를 보고 준 것이고, 고치면 안 된다.

## 11-25. 이름 칸에서 세 번 헤맨 끝에 — 자를 자리는 처음부터 하나였다

또 손걸이 나왔다. 이번엔 용원식 줄이다. **같은 사진인데** 내 환경에서는 용원식으로
읽히고 사용자 브라우저에서는 손걸로 읽혔다.

리포트의 값을 내 값과 나란히 놓아 보니 원인이 보였다.

```
r:2:2   내 환경 0.73   사용자 0.762
r:2:4   내 환경 0.57   사용자 0.62
r:2:6   내 환경 0.23   사용자 0.25
```

**같은 JPEG 이라도 브라우저가 다르면 어둡기가 0.03~0.05 씩 움직인다.** 그런데 당시
규칙은 "1.2배 이상 벌어진 자리만 자를 후보로 받는다" 였고, 내 환경에서 1.23배이던
자리가 사용자 환경에서는 1.15배가 됐다. **정답이 후보 목록에 오르지도 못했고**,
남은 건 손걸(0000101 — 어두운 칸이 둘뿐이라 아무 줄이나 바싹 자르면 튀어나오는
함정)뿐이라 그게 뽑혔다.

### 세 번의 실패는 전부 같은 실수였다

| | 무엇을 했나 | 왜 깨졌나 |
|---|---|---|
| 1차 | 손마킹용 문턱값(0.62)을 그대로 씀 | 인쇄된 칸은 그만큼 안 진하다 |
| 2차 | 그 줄에서 가장 많이 벌어진 곳에서 자름 | 밝은 쪽 꼬리가 길어 엉뚱한 데를 고름 |
| 3차 | 자를 만한 자리를 전부 시험 + 홀짝·명단으로 거름 | "1.2배" 조건에 정답이 걸림 |

셋 다 **"어디서 자를까"를 사진마다 새로 정하려 한 것**이 화근이었다.

### 그런데 데이터를 다 모아 놓고 보니

지금까지 실제로 잰 이름 칸 열세 줄(혼A 여섯 · 혼B 일곱)을 한자리에 놓았다.

```
칠해진 칸 중 가장 밝은 것    0.88
빈 칸   중 가장 어두운 것    0.93
```

**자를 자리는 처음부터 하나뿐이었다.** 0.9 하나로 자르면 열세 줄이 전부 맞는다.
후보를 뒤질 필요도, 홀짝으로 가려낼 필요도 없었다.

그리고 이 0.9 는 임의의 숫자가 아니다. 어둡기는 이미 **옆 칸 종이 색으로 나눈 뒤의
값**이므로(그것도 채널마다 따로 — 11-22), 0.9 는 곧 **"종이보다 10% 넘게 어둡다"**
는 뜻이다. 종이가 누렇든 조명이 어둡든 그대로 성립한다. 브라우저가 0.05 움직여도
0.88 과 0.93 사이의 골짜기는 그대로다.

`rowBitsByContrast()` 를 통째로 지우고 한 줄로 바꿨다.

```js
const idx = rowCodeValue(ratios.map((v) => (v < NAME_CUT ? 1 : 0)));  // NAME_CUT = 0.9
```

### 못 읽는 줄은 못 읽는다고 한다

혼 B 둘째 줄(신윤호)은 일곱 칸 중 둘이 **빈 칸보다 밝게** 찍혀 어떤 문턱값으로도
가를 수 없다. 그건 인쇄 문제지 판독기 문제가 아니다. 엉뚱한 이름을 내놓느니 비워
두고 사람이 고르게 한다 — 이름 못 읽은 줄은 화면에서 강조되고, 골라 주면 그 줄
숫자가 그대로 들어간다(11-21).

### 시험에 못 박았다

`tools/real-photo-check.mjs` 가 이제 **이름 여섯 개도** 대조한다. 명단에 없는
이름이 하나라도 나오면 실패다. 확인해 봤다 — 기대 명단의 조연우를 손걸로 바꿔
두고 돌리니 두 건을 잡고 종료코드 1 을 냈다.

| | 결과 |
|---|---|
| 혼 A 이름 | 6명 전원 ✓ |
| 혼 B 이름 | 6명 ✓ · **손걸 오독 없음** (신윤호 한 줄은 못 읽고 그렇다고 말함) |
| 조보규·박윤호 스물여섯 칸 | ✓ |
| 합성 시험 9종 | 9/9 · 어긋남 0 |

## 11-26. 이름 칸 버블을 키웠다 — 다른 칸은 하나도 안 움직이게

11-25 까지 이름 칸 판독을 세 번 고쳤다. 그때마다 내가 가진 사진에서는 맞고 다음
사진에서 깨졌다. 원인이 뻔했다 — **여유가 없었다.**

```
칠해진 칸 중 가장 밝은 것   0.88
빈 칸   중 가장 어두운 것   0.93
                          ↑ 여유 0.05
브라우저만 달라도 움직이는 폭  0.03~0.05
```

여유와 잡음이 같은 크기다. 이런 건 알고리즘으로 못 메운다. 버블이 작아서 생긴
문제라 **버블을 키우는 수밖에 없다.**

### 2.1×1.9mm → 3.2×2.6mm, 한 줄 → 두 줄

다른 칸과 같은 크기로 키우면 일곱 개가 가로로 안 들어간다(24.2mm 필요, 칸 안쪽은
18mm). 그래서 **4 + 3 두 줄로 접었다.**

```
가로  4×3.2 + 3×0.5 = 14.3mm   (18mm 안에 들어감)
세로  2×2.6 + 0.5   =  5.7mm   (선수 줄 높이 17.63mm — 번호·이름과 같이 놓아도 남음)
넓이  3.99mm² → 8.32mm²        (2.1배)
```

### 핵심 — 다른 열은 한 칸도 안 움직인다

선수 줄 높이는 `.prow` 의 `flex:1` 로 표 전체에서 **균등 분배**된다. 그래서 이름 칸이
커져도 줄 높이가 안 변하고, 나머지 열의 버블 자리도 그대로다. 재서 확인했다.

```
이름 칸(r) 이동   63개   ← 의도한 것
그 외 칸 이동      0개   (최대 0.000mm)
```

이게 지켜지는 덕분에 **이름 칸을 키우기 전에 뽑아 둔 종이도 숫자는 전부 그대로
읽힌다.** 붙박이 시험이 증거다 — 옛 사진에서 조보규·박윤호 스물여섯 칸이 여전히
사람이 확인한 값과 정확히 맞는다. 이름만 못 읽는다.

`sheet-readtest.html` 의 `__bubbleAnchor()` 가 이걸 지킨다. 출전·2점·리바운드·
맨 아랫줄·꼬리글 코드 다섯 자리를 **키우기 전에 잰 mm 값**과 대조한다.

### 옛 종이에는 뭐라고 말하나

"이름 칸이 없습니다 — 예전 양식입니다" 는 틀린 말은 아니지만 쓸모가 없다. 바꿨다:

> 이름 칸을 키우기 전에 뽑은 종이입니다 — **숫자는 다 읽었으니** 아래에서 줄마다
> 선수만 골라주세요. 다음 인쇄부터는 이름도 자동으로 읽힙니다.

이름 못 읽은 줄은 화면에서 강조되고, 골라 주면 그 줄 숫자가 그대로 들어간다(11-21).

### 잰 결과

| | 결과 |
|---|---|
| 다른 열 버블 이동 | **0개** |
| 합성 시험 9종 | 9/9 · 어긋남 0 · 이름 8명 |
| 옛 사진(붙박이) 숫자 | 조보규·박윤호 스물여섯 칸 ✓ |
| 옛 사진(붙박이) 이름 | 0줄 — **의도한 대가** |
| 아이폰 인쇄 | 세로 여유 16.3mm (그대로) |

새 양식으로 뽑은 종이에서 실제로 얼마나 나아지는지는 **다음 사진을 받아야 안다.**
버블 넓이가 2.1배이니 어둡기 여유도 그만큼 늘어야 맞지만, 그건 아직 잰 값이 아니라
예상이다.
